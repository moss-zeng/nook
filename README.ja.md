# nook

nook は、個人コレクター向けのローカルメディア管理ツール（Android）です。SMB プロトコルでパソコンや NAS 上の共有フォルダにアクセスし、そこに散らばった動画・画像・さまざまなコレクションを、コレクター自身が定めた構造に沿って整理し、並べ、味わえるようにします。再生そのものは担いません——作品をタップすると、スマホ側の外部プレイヤー（MX Player など）に引き渡します。

「nook」とは、人目につかない静かな一隅のこと——コレクターが大切な収蔵品のために設えた、自分だけの片隅。それがこのプロジェクトの名前の由来です。

## 解決したい課題

長年のコレクターの手元には、たいてい好きな電子コレクションが大量に溜まっていきます。動画もあれば、画像もあり、テキストもある。出どころも形式もバラバラで、ひとまとめにすると雑然として、分類しづらく、じっくり味わうのも難しい。既存のツールには、しっくりくるものがありません：

- **ギャラリー、VLC（画像／動画プレイヤー）**：一つずつ開いて再生することしかできず、「管理」とは到底呼べません。何百、何千という、種類もまちまちなコレクションを前にすると、なすすべがありません。

- **Solid Explorer、MT マネージャ（ファイルマネージャ）**：ファイルそのものの管理には十分ですが、コレクターにとっては専門的とは言えません。ファイルとフォルダしか認識せず、目に入るのはいつまでも長いファイル名の羅列だけ。直感的でもなければ、コレクションに情報（これは誰か、どれだけ好きか、いつ手に入れたか）を添えることもできません。整理はとりわけ骨が折れ、「味わう」どころではありません。

- **Jellyfin、Fladder（メディアライブラリ／スクレイパー。Fladder は Jellyfin 風のメディアライブラリクライアント）**：こちらは正反対の極にあります。映画やドラマのような公開コンテンツ向けに設計され、ネット経由でポスターやあらすじ、出演者情報などを自動取得することに頼っています。ニッチな、あるいは個人的なコレクションには、相性が悪いうえに情報が過剰です——マイナーな作品の多くは、そんな大量のメタデータを必要としないのに、これらのツールでは必要に応じてオフにすることもできません。さらに厄介なのは、ポスターなどのファイルをネット上のデータベースから乱暴に引っ張ってきてディレクトリに突っ込み、もとのフォルダをぐちゃぐちゃにしてしまうことです。

一方は機能が少なすぎて再生しかできないプレイヤー、もう一方は重すぎてディレクトリを汚すメディアライブラリ。コレクター気質でありながら、整然と秩序立っていることにもこだわる人にとっては、どちらの極も合いません。nook は、その中間にぽっかり空いた隙間を埋めるために生まれました：管理・展示・再生（外部プレイヤー）を一つにまとめ、きれいで、行儀がよく、コレクションそのものだけを扱うツール——あえて、すべてのファイルを管理する汎用マネージャにはなろうとしていません。

## 設計思想

### 二種類の共有フォルダ

nook はまず、SMB 共有フォルダにアクセスできるブラウザです。接続ページにパソコンや NAS のアドレスと認証情報を入力すれば、そこにある共有フォルダ（以下 share。コレクションライブラリのルートにあたります）が一覧表示され、中に入って内容を見て回れます。

ただし nook は share を二通りに扱います。違いは、その share のルートに `_styles.json` という名前のファイルがあるかどうかです：

- **ふつうの共有フォルダ**（`_styles.json` なし）：nook は何も仮定せず、フォルダとファイルをそのまま見て回れるだけ——ファイルマネージャに近い動きです。まだ形になっていないライブラリを整える段階に向いています。
- **スタイル共有フォルダ**（`_styles.json` あり）：nook は、すでにルールに沿って整理されたコレクションライブラリだとみなし、コレクターが定めた構造に沿って組み立てて見せます。

この判定は share を開いたときに自動で行われ、手動で切り替える必要はありません。以下で詳しく述べるのは、まさにこの「スタイル共有フォルダ」内部の構造です——それはソフトに固定で書き込まれているわけではなく、フォルダの組み方といくつかの取り決めファイルによって決まります。ソフトはそれを読み取って見せるだけです。この構造は作者自身のコレクション整理の習慣であり、プログラミングができる人なら、これを土台にコードを書き換えて、自分好みのやり方に差し替えることもできます。

### スタイルから始める

作者はコレクションを前にすると、まず「スタイル」で分けたくなります。だから nook の最上層は、時間でも種類でもなく、**スタイル**です。

スタイルの分け方は完全に好み次第——具体的でも、かなり抽象的でもかまいません。たとえばユング心理学の十二の元型（Innocent、Explorer……）で分けても、タロットの大アルカナ（The Fool、The Magician……）で分けてもいい。こうした分類はさらにグループにまとめることもでき、画面上では異なるグループが区切られて表示されます。

どのフォルダを最上層のスタイルとするか、それらをどうグループ分けするかは、ルートの `_styles.json` に記録します：

```json
{
  "styles1": {
    "name": "Jung's Twelve Archetypes Theory",
    "styles": ["Innocent", "Explorer", "Sage"]
  },
  "styles2": {
    "name": "Tarot Major Arcana",
    "styles": ["The Fool", "The Magician"]
  }
}
```

フィールド名（`styles1`、`styles2`）はグループを表し、それ自体は表示されず、画面上で区切るためだけに使われます。各配列の項目は、ルート直下に実在するフォルダに対応します。ここに登録されたフォルダだけが、スタイルとして画面に現れます。

### スタイルの下：人物

一つのスタイルの下には、個々の対象が並びます。もっとも多いのは「人物」——スタイル共有フォルダ内の一つのサブフォルダで、その人の作品が直接入っています：

```
スタイル共有フォルダ/
└── 人物1/                  （人物）
    ├── _cover.jpg          人物カバー（任意）
    ├── _person.json        メタデータ（任意）
    ├── .covers/            作品カバー（任意）
    ├── .gallery/           画像ギャラリー（任意）
    ├── personal_vlog.mp4
    └── travel_log.mp4
```

人物フォルダ内の `_cover.jpg` はその人のカバーで、見て回るときに一目で見分けられるようにします。

### スタイルの下：グループ

ですが、コレクションにはしばしば「グループ」もあります——それぞれの作品も、みんなで一緒に手がけた作品も持つ、人の集まりです。nook は、人物とグループをシンプルな取り決めで見分けます：あるフォルダが*さらにサブフォルダを含んでいれば*グループとみなし、その中のサブフォルダがメンバーになります。_サブフォルダを含まない_（作品ファイルだけの）フォルダは、個人とみなします。

```
スタイル共有フォルダ/
└── グループ/                （グループ：メンバーのサブフォルダを含むため）
    ├── _cover.jpg          グループカバー
    ├── メンバー1/           （メンバー。それ自体が一人の人物）
    │   ├── _cover.jpg
    │   ├── _person.json
    │   └── group_mv.mp4    みんなで作った作品。実体はここに置かれている
    └── メンバー2/
        ├── _cover.jpg
        └── _person.json    references を通じて、上の group_mv を指している
```

グループは現実的な問題をもたらします：一つの作品（たとえばグループ全員で作った映像）が、複数のメンバーに同時に属するのです。メンバーごとにコピーを置けば、容量の無駄になるうえ、保守も大変。nook のやり方はこうです：作品はそのうち一人のメンバーの下にだけ実体を置き、ほかのメンバーは _references_ でそれを指す。こうすれば実体は常に一つだけで済むのに、関係するすべてのメンバーのところに現れます——そして作品の情報は、実際にそのファイルを抱えているメンバーに常に帰属します。

### 作品とその情報

各人物の下には、作品そのもの（動画ファイル）が並びます。作品は自分のカバーを持てます。その人物の `.covers/` フォルダに、作品のファイル名にちなんだ名前で置きます（例：`.covers/group_mv.mp4.jpg`）。作品を表示するとき、nook は次の順に探します：`.covers/` 内の同名カバー → なければその人物の `_cover.jpg` → それもなければプレースホルダ画像。だから、作品ごとに丹精込めてカバーを用意しても、手を抜いても、どちらでも構いません。

作品の付加情報——日付、あらすじ、どれだけ好きか、そして先ほどの引用関係——はすべて、その人物の `_person.json` に記録されます：

```json
{
  "name": "メンバー2", // !!! 実際には name フィールドは存在しません。これはヒントのための注記で、表示される名前はフォルダ名そのものです
  "aliases": ["別のニックネーム"],
  "notes": "メモ",
  "items": {
    "personal_vlog.mp4": {
      "date": "2023-06-21",
      "description": "あらすじ",
      "love": "preferred",
      "lovedAt": "2024-03-15T20:31:00.000"
    }
  },
  "references": ["スタイル/グループ/メンバー1/group_mv.mp4"]
}
```

- `items` のキーは作品のファイル名で、その作品の日付・あらすじ・love（好きの度合い）を記録します。
- `love`（好きの度合い）は三段階：デフォルト（書き込まない）、`preferred`（好き）、`pinnacle`（最愛）。これらは単なるラベルではありません——**Keep** ページでは、preferred や pinnacle を付けた作品だけが一カ所に集められ、ライブラリ全体をかき分けることなく、もっとも大切な作品にいつでもすぐ戻れます。
- `lovedAt` はその作品をお気に入りに付けた時刻で、アプリが自動的に書き込むので、手で編集する必要はありません。Keep ページでは、これを手がかりにお気に入りを保存した時系列でふり返れます。
- `references` の各項目は作品への絶対パスで、スタイルの層から書き始めます（share 名は含めない）。ほかの人物の下にある作品を、いまの人物に引いてくるために使います。

love、あらすじ、日付は、いずれもスマホで作品を開いたあとにその場で編集でき、変更はただちに `_person.json` に書き戻されます。もっと込み入った設定（メンバーをまたぐ引用関係など）は、パソコンでファイルを直接編集して行います。これらはすべて実ファイルへの直接の変更で、インポート／エクスポートも、独立したデータベースもありません——コレクションのデータは常にコレクションと一緒にあり、nook を離れてもそのまま完全に読めます。

### 必要に応じて、強制ではなく

これらの取り決めファイル（`_person.json`、`_cover.jpg`、`.covers/` など）は、すべて任意です。nook はデフォルトでは、フォルダとファイルをありのままに見せ、事前に何も用意することを求めません。作品にカバーを設定したい、お気に入りを付けたい、あらすじを書きたい——そう思ったときにだけ、対応する場所にファイルが生成されます。この慎ましさこそが肝心で、スクレイパーのようにディレクトリを冗長なファイルで埋め尽くしてしまう事態を避けるためのものです。（ちなみに `.covers/` フォルダが、グループのメンバーと誤認されることはありません。）

そのため、コレクションライブラリのルートには、スタイルのフォルダのほかに、`_` で始まるいくつかの特別な領域があります（`_` または `.` で始まるフォルダは、スタイルの内容としては表示されません）：

```
スタイル共有フォルダ/
├── _styles.json      スタイル登録表
├── _inbox/           インボックス：まだ分類していないものを一時的に置く場所（任意）
├── _blindbox/        ブラインドボックス：構造を問わず、すべてを平らに並べて気軽に眺める（任意）
├── Style1/           スタイルフォルダ1（任意）
├── Style2/           スタイルフォルダ2（任意）
└── ...
```

**ブラインドボックス**は、今は整理する気になれないもの、あるいはそれほど好きではないけれど捨てるには忍びないものを入れておく場所。**インボックス**は、まだ分類していないものをとりあえず積んでおくための場所です。

```
ある人物/
├── _cover.jpg          人物カバー（任意）
├── _person.json        メタデータ（任意）
├── .covers/            作品カバー（任意）
├── .gallery/           画像ギャラリー（任意）
├── personal_vlog.mp4
└── travel_log.mp4
```

そして各人物フォルダの下の `.gallery/` は、その人物の**画像ギャラリー**です——コレクションは動画だけではないので、画像やさまざまな雑多な収蔵品もここに入れられます。画像は専用のギャラリー画面で眺め、それ以外のファイルはふつうのモードに切り替えて見られます。

最後に、nook が行う操作は移動とリネームだけで、**いかなるファイルも決して削除しません**——これが、コレクターに対する最も基本的な安全の約束です。

## 開発環境とビルド（ソースから実行する）

ふだん使うだけなら、公開されている APK をインストールするだけで十分で、コンパイルは不要です。以下は、ソースから実行・改変したい開発者向けです。

環境（Windows、Android Studio 不要）：

- Git
- OpenJDK
- Flutter SDK（stable）
- Android SDK コマンドラインツール（platform と build-tools）

設定が済むと、`flutter doctor` の Flutter と Android toolchain の二項目が、いずれも利用可能な状態になっているはずです。

スマホでデバッグ実行する：

1. スマホで開発者オプションと USB デバッグを有効にし、ケーブルでパソコンに接続します。
2. プロジェクトのルートで次を実行します：

   ```
   flutter pub get
   flutter run
   ```

3. 必要に応じてコードを変更します。
4. APK をビルドします：

   ```
   flutter build apk --release
   ```

生成されたファイルは `build/app/outputs/flutter-apk/app-release.apk` にあります。
